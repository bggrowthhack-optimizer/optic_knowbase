# Плейбук: как пошагово описать задачу для разработки (Главная / «Анализ филиала»)

Это инструкция для Claude в новом чате. Цель: вести пользователя по одной задаче шаг за шагом, **задавать вопросы вместо того, чтобы придумывать**, и в конце выдать однозначный текст, который пользователь целиком вставит в YouGile.

Контекст: редизайн «Главной» (РОП и КД) в продукте Optimizer согласован по блокам и лежит в ТЗ. Его нужно превратить в отдельные задачи для разработчиков. Уже описаны текстом: общий «Редизайн Главной», «План задач на сегодня», «Контрольная точка», «Быстрый перенос задачи». Осталась группа задач про окно «Анализ филиала».

## 2. Подключение к GitHub

1. Репозиторий `optic_knowbase` обычно уже в сессии. Если нет — вызови `add_repo` (owner `bggrowthhack-optimizer`, repo `optic_knowbase`, access `read`), клонируй командой из ответа и вызови `register_repo_root`.
2. `gh` и `hub` недоступны. Все операции с GitHub — только через инструменты `mcp__github__*` (чтение файла: `get_file_contents` с `ref=claude/friendly-goldberg-2bk9zq`).
3. Не проверяй существование репозитория через `curl` / `git ls-remote` — приватный репозиторий вернёт 404 даже при наличии доступа.
4. Другие репозитории организации (`opti-kb`, `family_bot`, `motivation-calculators`, `roadcast`) к этой работе не относятся — не читать.
5. Писать в репозиторий **только когда пользователь скажет «сохрани»**: ветка `claude/friendly-goldberg-2bk9zq`, в конце коммита — подпись из системного напоминания сессии, push с `-u origin <ветка>`. PR не создавать, пока не попросят. Если PR по ветке уже влит — начать заново от актуальной default-ветки с тем же именем ветки.

## 3. Жёсткие ограничения

1. **Ничего не выдумывать.** Любое решение по логике, дизайну, тексту — только после ответа пользователя. Нет ответа — в тексте пишем «уточняется», а не придумываем.
2. Вопросы задавать через `AskUserQuestion` с вариантами (пользователь может ответить своими словами). Если ответ непонятен или оборван — **не считать подтверждением**, переспросить.
3. Текст задачи — **только в чате**. Не писать в файл («Не пиши никуда, я в юджайл перенесу»). Файлы меняем только по «сохрани» (ТЗ и журнал).
4. **Без блока «Как проверить».**
5. **Каждый пункт описан словами в самом тексте.** Никаких «см. ТЗ», ссылок на файлы и ветки, коротких саммари вместо содержания. Ссылаться можно только на **названия других задач**.
6. Простой язык, без канцелярита: «ВТЛ» (высокотехнологичные линзы, не «вторая пара»), без «при плане». Точные тексты надписей — в кавычках, как будут на экране.
7. Роли: РОП и КД. Прототип работает в демо-режиме только на чтение (PUT → 403) — это про прототип, не про требования.
8. Помечать статус каждого пункта (для себя, в итоговый текст значки не выводить):
   - ✅ согласовано — формулировать как требование;
   - ⚠ предварительно — писать «значение уточняется: …»;
   - ❓ открыто — выносить в «Не входит / решим отдельно».
9. Границы между задачами: если пункт принадлежит другой задаче, оставить здесь только место и связку (как с кнопкой «Перенести»), а подробности — в «Не входит» с названием той задачи.

## 4. Реестр задач

Осталось описать, **в таком порядке**:

| # | Задача | Блок ТЗ | Зависит от |
|---|---|---|---|
| 1 | Анализ филиала → «Обзор месяца» (план по очкам, «Что мешает плану», «К прошлому месяцу»). Первой: только просмотр, без зависимостей. В начале решить открытый вопрос — считать «Что мешает плану» по формуле или скрыть в первой версии | Блок 8, вкладка месяца | — |
| 2 | Анализ филиала → «Обзор смены» (включая механизм «Требуют внимания», отметки «Разобрал» / «Задача поставлена») | Блок 8 (общее + вкладка) | — |
| 3 | Карточка филиала: тег «N требуют внимания» | Блок 5, п.2–4, 6 | 2 |
| 4 | Анализ филиала → «Обзор трендов» (таблица «Как менялось» + «Кто тянет вниз») | Блок 8, вкладка трендов | 2 |

Каркас окна (заголовок «Анализ филиала · <филиал>», три вкладки в порядке «Обзор смены» → «Обзор месяца» → «Обзор трендов», на какой вкладке открывается окно) в задачу «Обзор месяца» не входит. Спроси пользователя, куда его отнести (вероятно, в «Обзор смены» как в первую вкладку).

Открытые вопросы из ТЗ, которые всплывут (решать только ответами пользователя): правило попадания в «Требуют внимания»; правило «Кто тянет вниз»; формула «Что мешает плану» (считать или скрыть в первой версии); список «типовых задач» (5–7 шаблонов). Отдельно в журнале лежит запрос Надин (разбивка воронки по сотрудникам, загрузка врачей, микрозадачи) — **не реализовано**, в эти задачи не включать, пока пользователь не скажет.

После всех четырёх задач: убрать из общей задачи «Редизайн Главной» куски про «Анализ филиала» и заменить ссылками на названия этих задач.

## 5. Цикл работы над одной задачей

**Шаг 0. Рамка.** Кратко (5–7 строк) пересказать, что уже согласовано по задаче из ТЗ, и назвать, от каких задач она зависит. Ничего нового не добавлять. Пользователь поправляет.

**Шаг 1. Зачем.** Спросить словами пользователя: какую проблему РОП/КД решает этот блок, что делает сегодня вместо него. Это пойдёт в начало описания.

**Шаг 2. «Сейчас».** Выписать текущее поведение из `demo-code` / ТЗ («Сейчас: …»). Чего не видно в коде — спросить, не додумывать (при необходимости попросить zip).

**Шаг 3. Проход по элементам сверху вниз.** По каждому элементу: что показываем (точные тексты, числа, цвета), что происходит по клику, откуда берутся данные. На каждый пробел — вопрос с 2–4 вариантами. Вести таблицу ✅ / ⚠ / ❓ и показывать её в конце шага.

**Шаг 4. Чеклист краёв** (каждый пункт — вопрос, если ТЗ молчит): пустое состояние; ошибка загрузки; телефон; что сохраняется и **на кого или что** (на пользователя, филиал, смену) и видят ли это другие РОП/КД; сброс при повторном открытии; прошлые периоды; что считать «первым днём» и недостатком данных; кто видит блок (РОП / КД).

**Шаг 5. Границы.** Что входит, что не входит, какие задачи рядом и как называются. «Не входит» — списком.

**Шаг 6. Черновик.** Выдать текст в чате по шаблону ниже. Пользователь правит, переписывать целиком (не «патчем»), пока не скажет «ок».

**Шаг 7. Закрытие.** Предложить: (а) обновить `tz-glavnaya.md` / `home-redesign-rules.md`, если решения поменялись; (б) убрать этот кусок из общей задачи «Редизайн Главной». Делать только по «сохрани» / «да».

### Шаблон итогового текста (для YouGile)

1. **Название** — «Главная / Анализ филиала — <что>».
2. **Описание**: зачем это нужно (1–3 предложения, словами пользователя) → что сейчас → что делаем.
3. **Что нужно** — по элементам сверху вниз, полными предложениями: что видно, точные надписи в кавычках, формулы и пороги (или «значение уточняется: …»), поведение по клику, что сохраняется, пустые и граничные состояния, телефон.
4. **Связи с другими задачами** — по названиям.
5. **Не входит в эту задачу** — список с названием той задачи или решения, куда уехало.

Без «Как проверить», без ссылок на файлы.

### Банк вопросов по задачам (это вопросы, не ответы)

**1. Обзор месяца:** формула «Что мешает плану» (считать или скрыть в первой версии); пороги слов «успеваем / чуть отстаём / заметно отстаём»; источник «зоны» филиала; какие дни сравниваются с прошлым месяцем при разной длине месяцев.

**2. Обзор смены:** что такое «смена» (календарный день?); откуда «Рекомендация аналитики» и маршрут из 2 шагов (существующий `TaskRecommendationBlock` / типовые действия?); как формируются короткие фразы по показателю; правило попадания в «Требуют внимания» (с кем сравнивать, период, порог, учёт потока клиентов, минимум данных); где хранятся «Разобрал» / «Задача поставлена» — на пользователя или на филиал+смену, видны ли другим; чем предзаполняется форма «Поставить задачу»; формула «Нужно в день» и граничные случаи (последний день месяца, нет плана); что при пролистывании на прошлые смены остаётся и что исчезает.

**3. Тег на карточке:** обновляется ли счётчик сразу после постановки задачи / «Разобрал»; кого считать при отсутствии данных; поведение для КД (много филиалов).

**4. Обзор трендов:** как определяется «в сети ровно / падает у всех» (что такое «сеть», порог); правило «Кто тянет вниз»; порог «стабильно» (~3% в ТЗ — подтвердить); отметки «Разобрал» отдельные от смены — подтвердить хранение.
